# 集群权限空间关系设想

状态：**讨论稿**。存在性与内容已经按第 4 节拆开并实现；分组、profile、回执动作仍未做。求值顺序以 [重构说明.md](重构说明.md) 为准：先看具体 peer，再看 `*`，同一层里拒绝压过允许，写不随 `default: allow` 打开。

相关文档：[重构说明.md](重构说明.md)、[全流程设计.md](全流程设计.md)。

## 1. 绝对去中心化

这是所有设计的前提，不是口号：

- **没有全局权限表。** 每个节点的配置只决定“别人能对我做什么”。
- **没有中心注册表。** 社区不是一份名单，而是一张由 bootstrap 和邻居关系连起来的图。
- **没有中心审计。** 每个节点自己留痕，不汇总到任何地方。
- **没有中心 UI。** 每个容器自己的 billui 是独立视角。
- **没有中心执行者。** 没有任何节点能替别的节点做决定或代表别的节点发言。

绝对去中心化有一个必须接受的后果：**协议只能约定，不能强制执行。** 一个节点可以修改自己的程序、违反约定；其他节点能做的只有“观察到并拒绝与它交互”。没有中心来惩罚它。

所以本文里的“不可关闭”“必须开放”，都是**协议约定 + 对等选择**，不是技术上的强制。

## 2. 社区与关系

社区不是目录服务，而是**关系图**：

```
apple ──bootstrap──> banana
  │                    │
  └──工单往来────────> peach
                       │
                     chili
```

关系至少有四种：

| 关系 | 含义 | 是否等于信任 |
|---|---|---|
| bootstrap 关系 | 我从谁那里拉名录 | 否 |
| 邻居关系 | 名录里互相可见 | 否 |
| 工单往来 | 一起完成过某张工单 | 否 |
| 权限关系 | 我允许你对我做什么 | 是（有方向的有限信任） |

几个约束：

- 关系是**有方向**的：apple→banana 和 banana→apple 是两条独立的关系。
- 关系**不可传递**：apple 认识 banana、banana 认识 chili，不推出 apple 认识或信任 chili。
- 关系**不隐含信任**：认识只代表可发现；能不能做事由权限决定。
- 社区**没有成员名单**：谁在社区里，是观察到的关系图，不是某个中心发的成员资格。
- 一个节点可以处在多个社区：靠不同的 `network` 域隔离，不同域的记录互相丢弃。

## 3. 权限是一个有向标记图

把节点看作顶点，权限看作有向边：

```
B ── tickets.list, config.read ──> A
C ── config.*, tickets.* ────────> A
A ── tickets.get ─────────────────> C
```

一条边 `X → Y` 表示：**Y 允许 X 对它执行哪些动作**。边权是动作集合。

四个性质：

1. **有方向**：A→B 和 B→A 是两条独立的边，由两个节点各自的配置决定。
2. **非对称**：单边允许不需要对方同意。
3. **非传递**：A 信任 B、B 信任 C，不推出 A 信任 C。
4. **局部知识**：每个节点只知道自己的出边策略，没有人持有完整矩阵。

矩阵表示，行是目标，列是请求者：

| 目标 \ 请求者 | B | C |
|---|---|---|
| **A** | `tickets.list`, `tickets.get`, `config.read` | `tickets.*`, `config.*` |
| **B** | — | — |
| **C** | `tickets.get` | — |

这张表只存在于三个节点各自的配置里。

## 4. 分层可见性

当前主流产品几乎都不使用“全局读开关”，而是把**存在性**和**内容**分开。这里采用同样的分层：

| 层 | 内容 | 可见性 | 例子 |
|---|---|---|---|
| 1. 身份与能力 | 我是谁、能做什么、是否在线 | 社区内公开，**协议约定不可关闭** | `node.info`、`peers.list`、描述、在线状态 |
| 2. 工作元数据 | 有没有工单、走到哪、回执 | 社区内公开，**协议约定不可关闭** | `tickets.list`、`tickets.receipts`、状态 |
| 3. 内容 | 表单、交付物、配置、日志 | 可配置 | `tickets.get`、`config.read`、`logs.read` |
| 4. 动作 | 发起、派单、改派、改配置 | 可配置 | `tickets.create`、`config.write`、`wake` |

含义：

- **第 1、2 层做“三体人”**：不能假装没有工作发生，不能拒绝别人知道“你这里有一张工单”；
- **第 3、4 层做“人类”**：内容可以保密，动作可以拒绝；
- UI 可以显示“apple 有 3 张工单，其中 2 张内容不可见”，而不是假装没有。

这不是新发明，而是主流产品的共同结构：公开工作图 + 私密内容 + 可控动作。

## 5. 主流产品对照

| 产品 / 协议 | 存在性 | 内容 | 动作 | 值得借鉴 |
|---|---|---|---|---|
| Matrix | 房间成员可见 | 房间级 history visibility（world_readable / shared / invited / joined） | 房间权限 | 可见性按作用域，E2EE 与可见性分离 |
| Mastodon / ActivityPub | 按帖子可见性投递 | public / unlisted / followers / direct | 关注关系 | 发送时决定可见性；联邦副本删除只是建议 |
| Bluesky / AT Protocol | 仓库默认公开，Relay 抓取 firehose | 公开记录 + 独立加密私信 | 标签与审核 | 公开工作图 + 审核标签 + 独立私密通道 |
| Nostr | 事件默认公开 | NIP-17 gift wrap 加密私信 | Relay 可要求 NIP-42 认证 | 公开外壳 + 加密内容；删除是请求 |
| Solid / WAC | 每资源独立 | 每资源 ACL：read / write / append / control | 每资源 | 默认拒绝；数据主权在所有者 |
| A2A（Google） | Agent Card 公开 | 基础卡公开，认证后看扩展卡 | OAuth2 / OIDC / mTLS | 两级卡：公开能力 + 认证后详情 |
| Linux / SSH | 主机存在 | 按文件 ACL | 按 key / 命令 | 默认拒绝、逐 key 授权、审计 |

共同点：

1. 存在性与内容分离；
2. 可见性按作用域（房间、资源、帖子），不是全局开关；
3. 访问控制默认拒绝（社交信息流除外）；
4. 删除和撤回都是建议性的；
5. 开放系统靠审核和标签，不靠硬性拒绝；
6. 协议不保证结果真实，任务状态是自我上报的。

## 6. 动作目录

按层划分动作：

| 层 | 动作 | 是否可关闭 |
|---|---|---|
| 1 | `node.info` | 否（协议约定） |
| 1 | `peers.list` | 否（协议约定） |
| 2 | `tickets.list` | 否（协议约定） |
| 2 | `tickets.receipts` | 否（协议约定） |
| 3 | `tickets.get` | 是 |
| 3 | `config.read` | 是 |
| 3 | `logs.read`（未来） | 是 |
| 4 | `tickets.create` | 是 |
| 4 | `tickets.redispatch` | 是 |
| 4 | `tickets.void` | 是 |
| 4 | `config.write` | 是 |
| 4 | `wake` | 是 |

支持模块通配：`tickets.*`、`config.*`。

“不可关闭”是对等约定：节点可以改程序违反它，但其他节点会观察到并拒绝与它交互；没有中心来强制。

## 7. 规则与求值

一个节点的配置：

```json
"access": {
  "default": "allow",
  "groups": {
    "admin": ["peer_b"],
    "worker": ["peer_c"]
  },
  "rules": [
    {"group": "admin", "allow": ["config.*", "tickets.*"], "deny": ["tickets.void"]},
    {"group": "worker", "allow": ["tickets.list", "tickets.get"], "deny": ["config.*"]},
    {"peer": "peer_x", "deny": ["logs.read"]}
  ]
}
```

求值顺序：

1. 命中任意 `deny` → 拒绝；
2. 命中任意 `allow` → 允许；
3. 否则用 `default`。

更具体的规则优先于更宽泛的规则（具体 peer > 分组 > 通配），但 **deny 始终压过 allow**。

### 7.1 分组是本地标签

- `groups` 只存在于节点自己的配置里；
- A 把 B 叫“admin”，B 不知道，也不会因此获得对 C 的权限；
- 分组类似 Unix 的 group，只为少写规则。

不要把“角色”发布到名录里，否则信任关系图就泄露了。

## 8. 社区 profile

社区可以声明自己的可见性约定，但它只是**每个节点本地的声明 + 对等选择**，没有中心执行者：

| profile | 第 1、2 层 | 第 3 层 | 第 4 层 |
|---|---|---|---|
| `transparent` | 公开 | 默认公开 | 默认公开 |
| `hybrid`（默认） | 公开 | 默认公开，可拒绝 | 默认公开，可拒绝 |
| `private` | 公开 | 默认拒绝，按 peer 放行 | 默认拒绝，按 peer 放行 |

- profile 写在节点自己的配置/节点信息里；
- 其他节点可以据此决定是否与它交互；
- 节点可以声称一个 profile 却行为不一致，其他节点只能靠观察和拒绝来应对；
- 没有任何中心来验证或强制执行 profile。

## 9. 邻居、可见性、可达性

三个不同的轴：

| 轴 | 回答 | 存在哪里 |
|---|---|---|
| 发现 | 我知不知道你 | 名录（peer 记录） |
| 可达 | 现在能不能连上 | 网络 / 唤醒状态 |
| 允许 | 你能不能对我做事 | 本节点的 `access` 配置 |

组合：

| 情况 | UI 表现 |
|---|---|
| 知道 + 在线 + 允许 | 正常查看 |
| 知道 + 在线 + 拒绝 | “拒绝访问” |
| 知道 + 离线 | “离线 / 不可达” |
| 不知道 | 不出现在名录里 |

两个约定：

- **拒绝不等于从名录消失。** 否则授权就变成了隐形封禁。
- **离线不展示最后快照。** 数据只在节点自己手里，不存在副本。

## 10. 传递、代理与去中心化边界

- 不传递：A→B、B→C 不产生 A→C。
- 不代理：B 不能“代表” A 向 C 请求；C 看到的请求者永远是 B。
- 人也不改变这一点：人登录 A 的 billui，跨节点请求仍由 A 的节点身份签名，C 检查的是 A。
- 如果 A 想访问 C，必须由 C 明确允许 A；不能借道 B。

绝对去中心化还意味着：

- 没有中心能强制一个节点遵守 profile；
- 没有中心能保证“存在性一定被公开”——修改过的客户端可以隐瞒、延迟、离线；
- 对等节点能做的只有：观察、拒绝、不再与它合作。

## 11. 审计

每个远程控制请求都带签名、来源和动作。目标节点本地记录：

```json
{"ts": ..., "from": "peer_b", "action": "config.write",
 "target": "self", "result": "deny", "envelope_id": "..."}
```

- 允许和拒绝都记；
- 不汇总到中心，每个节点自己留痕；
- 默认全开的部署里，审计是唯一能回答“谁改了什么”的东西；
- 回执和审计可以互相印证，但签名只证明“谁说的”，不证明“内容真实”。

## 12. 资源粒度

第一版是节点级：

- `tickets.list` = 列出本节点持有的工单；
- `tickets.get` = 查看本节点持有的任意工单。

因为不复制工单，A 持有的只有 A 自己发起的工单；B 看到的是“A 的视角”，不是全网视图。

工单级 ACL 暂不做：它会把二维权限矩阵变成三维，复杂度明显上升。

## 13. 与 billgo / billui 的关系

- **billgo** 执行权限：验签、按 `access` 求值、审计；
- **billui** 只展示：请求由本机 billgo 发出，UI 不持有权限逻辑；
- **CLI** 与 billui 能力对等；
- `access` 配置只存在本地，不进入名录；
- UI 展示的是“本节点对某个 peer 的有效权限”，拿不到对方的完整策略。

## 14. 默认全开的代价

默认 `allow` 意味着：

- 新节点上线即可被任何可达 peer 读取，甚至修改配置；
- 忘记写 deny 就是敞开的；
- 启动时应打印警告，说明当前 `access.default` 和 `config.write` 的状态；
- 社区只能靠约定和对等拒绝来维持，不会有中心来兜底。

安全不是当前阶段的重点，但默认行为必须让人看得见。

## 15. 暂不做

- 全局角色 / 集群级 RBAC；
- 权限传递、代理、委托；
- 能力令牌（macaroon / UCAN）式授权；
- 工单级、跳级 ACL；
- 按来源 IP、时间窗口、请求频率的限制；
- 跨 `network` 域的联邦权限；
- 公开事件公告 / 全量复制（“存在性不可隐瞒”的强保证）。

## 16. 待定

1. profile 是否进入签名的节点信息，供 peer 判断；
2. 第 3、4 层的默认值是全开还是按 profile 决定；
3. `access.rules` 用数组。已实现。
4. `config.write` 默认关闭，不随 `default: allow` 打开。已实现。
5. `allow_from` 继续管派单，不并入 `access`。
6. 工单级 ACL 的时间点；
7. 审计按 8MB 轮转，保留 3 个旧文件。已实现。
8. 拒绝、离线、超时不自动重试。内容被拒时列表仍在，详情显示「内容不可见」。已实现。
9. 是否需要“拉黑”这种一键拒绝所有可关闭动作的快捷配置。`tickets.*` 不能用来关列表，因为列表属于公开层。

## 17. 一句话

**绝对去中心化下，权限是每个节点自己维护的有向图：存在性靠协议约定尽量公开，内容与动作靠本地策略控制；社区是关系网，不是名单；没有中心能强制任何事，只有对等拒绝。**
