# billgo → billgo + billui 重构说明

状态：**阶段一至五已实现**。

目标：把 UI 从 billgo 核心剥离出去，形成两个工具——`billgo` 负责节点与执行，`billui` 只做界面。两者打包在同一个容器里，`billui` 依赖 `billgo`，但 `billgo` 可以完全不启动 UI。

## 1. 背景

当前 `billgo` 内置了 `internal/webui`：页面、接口、状态计算都在守护进程里，只能看本机内容。

这套实现有几个根本问题：

- UI 和核心耦合，UI 的迭代、鉴权、页面安全都会影响核心；
- 页面只能看本机数据，看不到邻居；
- “去中心化的透明社区”需要跨节点查看，而当前控制面只在本机 Unix socket 上；
- UI 不是必需能力，却和节点一起启动、一起打包、一起测试。

## 2. 目标

- **billgo**：身份、名录、工单、执行、投递、远程控制 API、CLI。没有 UI。
- **billui**：独立的 UI 服务，依赖 billgo；登录、展示、发起、改派、改配置都通过 billgo。
- **同一个容器**：`billgod` + `billui` 两个进程，`billui` 可选。
- **不复制工单**：工单仍然只存在发起者容器里；发起者宕机，邻居看不到，唤醒后才能看。
- **实时聚合**：任意节点的 billui 通过 billgo 实时查询可达节点，看到的是当前可达范围内的内容。
- **按需加载**：禁止全量查询，先选节点，再分页加载它的配置和工单。
- **权限在个体**：读默认允许，写默认拒绝。每个节点可以按动作放行或拒绝任何 peer。
- **社区透明**：可访问范围内的工作和状态对所有节点可见；被拒绝或离线的节点显示不可用，不显示最后快照。

## 3. 架构

```
┌──────────────────────── 容器 A ────────────────────────┐
│                                                        │
│   billui ── Unix socket ──> billgod                    │
│                                │                       │
└────────────────────────────────┼───────────────────────┘
                                 │ 签名控制信封（TLS + 指纹固定）
                                 ▼
                        邻居的 billgod
                                 ▲
                                 │
                        容器 B 的 billui
```

- `billui` 只和本机 `billgod` 对话；跨节点查询由 `billgod` 发起。
- 远程请求使用节点自己的 ed25519 身份签名；目标节点按**发起节点**的 peer_id 做权限判断。
- 没有中心、没有全局索引、没有上报。节点不知道谁会起 UI，也不知道谁在查自己。

## 4. 核心原则

1. **能力在 billgo，billui 只是壳。**
   billui 能做的任何事，CLI 必须能同样做到；billui 不实现业务逻辑，也不维护权威状态。

2. **不复制工单。**
   权威数据留在发起者/执行者本地。透明是实时查询，不是同步副本；节点离线即不可见。

3. **权限在个体。**
   每个节点自己的配置决定谁能读、谁能写；没有中心 ACL。

4. **按需查询。**
   不提供“加载所有节点/所有工单”。查询按 peer、分页进行。

5. **远程操作必须可审计。**
   每个远程读写请求都有签名、来源、动作、结果；本地留痕。

6. **billui 启动依赖 billgo。**
   billgo 不感知 billui；billui 连不上 billgo 就明确报错或重试。

## 5. 权限模型

### 5.1 动作目录

权限按**动作**划分，不按“读/写”两档。

| 模块 | 动作 |
|---|---|
| node | `node.info` |
| peers | `peers.list` |
| tickets | `tickets.list`、`tickets.get`、`tickets.create`、`tickets.redispatch`、`tickets.void` |
| config | `config.read`、`config.write` |
| wake | `wake` |
| logs（未来） | `logs.read` |

动作清单是长期演进的接口，新增能力时追加动作，不改已有语义。

### 5.2 配置形状

```json
"access": {
  "default": "allow",
  "rules": [
    {"peer": "peer_x", "deny": ["config.write", "tickets.create"]},
    {"peer": "peer_y", "allow": ["tickets.list", "tickets.get", "config.read"]},
    {"peer": "*",      "deny": ["logs.read"]}
  ]
}
```

判定顺序：

1. 先看**这个 peer 自己**的规则。同一层里只要有 `deny` 命中该动作就拒绝；只有 `allow` 命中才允许。这条规则没提到的动作，继续往下看，不把整条规则当成“只允许这里列出的动作”。
2. 再看 `peer: "*"`，规则同上。
3. 都没提到时：读动作用 `default`；写动作拒绝。`default: allow` 不会打开写。

支持模块通配：`tickets.*`、`config.*`、`wake.*`、`logs.*`。`wake.*` 含动作 `wake`。

- `default` 允许 `allow` / `deny` 两种值；省略时按 `allow`，并且只作用于读。
- 写动作是 `tickets.create`、`tickets.redispatch`、`tickets.void`、`config.write`、`wake`。其余当前动作为读。
- 这与现有的 `allow_from` 是两件事：`allow_from` 管“谁能派单给我”，`access` 管“谁能查我/改我”。

### 5.3 读开写关

读默认允许，是为了可访问范围内的工作彼此可见。写默认拒绝，避免新节点一上线就被改配置或塞工单。

仍要接受：

- 忘记配 deny，邻居就能读到工单和配置；
- 写必须出现在某条规则的 `allow` 里才会放行，包括 `peer: "*"`；
- 审计是必需品，否则无法回答“谁读过、谁被拒绝”。

### 5.4 审计

每个节点本地写 JSONL 审计日志：

```json
{"ts": 1700000000000, "from": "peer_x", "action": "config.write",
 "target": "self", "result": "allow", "envelope_id": "..."}
```

- 允许和拒绝都记；
- 远程请求本身是签名信封，可作为不可抵赖的证据；
- 日志在 `<data_dir>/audit.jsonl`，权限 0600。超过 8MB 轮转，保留最近 3 个旧文件；
- 同一个请求 id 的重试只记第一次：幂等缓存直接返回上次结果；
- 查看是本机能力：`billgo audit` 和 billui 的审计页。不通过远程 `logs.read` 给邻居；
- billui 另外记录登录成功/失败（密码每次启动都变）。

## 6. billui

### 6.1 登录

- 只需要一个密码，不建账号体系。
- 密码由 billui 每次启动随机生成，**不保存旧密码**。
- 启动时打印到日志，并写入 `<data_dir>/billui.password`（0600）。
- 登录成功后发 session cookie；billui 重启后所有会话失效。
- 忘记密码就重启 billui。

### 6.2 两种身份，不要混淆

```
人 ──密码──> 本机 billui ──节点签名──> 邻居的 billgod
```

- 密码只证明“谁在用这台机器的 UI”；
- 跨节点请求由本机节点签名，邻居检查的是**本机节点的 peer_id**；
- 邻居拒绝本机节点时，人只能手动打开邻居的 billui（输入邻居的密码），不能通过本机 UI 越过权限。

### 6.3 页面

- 默认展示本节点：状态、配置摘要、工单。
- 名录里选择邻居，按需加载它的配置和工单。
- 工单列表必须分页（`limit` + `cursor`），没有“加载全部”的入口。
- 被拒绝显示“拒绝访问”；不可达显示“离线/不可达”；超时显示“超时”。都不自动重试，页面给「再试一次」，点下去才再问，不展示最后快照。
- 可执行动作：发起、改派、作废、修改配置；全部通过 billgo 的远程控制 API。

### 6.4 监听与访问

- 不再强制 loopback；`billui.listen` 可以监听任意地址。
- 必须配置登录密码；没有密码时拒绝启动，或由启动流程生成随机密码。
- 页面本身不做账号、角色，只有“已登录/未登录”。

## 7. 远程控制协议

不另做消息格式。控制请求就是现有签名信封，`type` 为 `ctl.request` / `ctl.response`。`to` 是目标 peer_id，动作放在 `body` 里：

```json
{
  "v": 1,
  "type": "ctl.request",
  "from": "<发送者公钥 base64>",
  "to": "<目标 peer_id>",
  "ts": 1700000000000,
  "body": {
    "id": "<uuidv7>",
    "action": "tickets.list",
    "args": {"limit": 20, "cursor": "..."}
  },
  "sig": "<ed25519 签名 base64>"
}
```

- 请求由发起节点签名；目标节点验签后按发送者的 peer_id 做权限判断。
- `ctl.*` 和 `hop.*` 一样受 5 分钟时间窗约束。名录消息仍然不看时间。
- 幂等键是 `body.id`。重复送达返回上次的签名响应，不重复执行。
- 读动作把数据放进响应 `body.data`。权限或参数错误也回一封签名的 `ctl.response`，用 `error_code` 区分，而不是裸的 HTTP 500。
- 分页：`limit` 默认 20，服务端上限 100。`cursor` 不透明，内容是上一页最后一条的 `updated_at` 和工单号。
- 读动作：`node.info`、`peers.list`、`tickets.list`、`tickets.get`、`config.read`。
- `node.info`、`peers.list`、`tickets.list` 按约定公开。判定始终放行；规则里拒绝它们（含 `node.*`、`peers.*`、`tickets.*`）时配置加载失败。
- `tickets.list` 只返回状态、跳和时间。表单、跳的描述和交付物在 `tickets.get`，可以拒绝。拒绝内容时列表仍然可见。
- 写动作：`tickets.create`、`tickets.redispatch`、`tickets.void`、`config.write`。本机 Unix socket 直接执行；远程请求先过 `access`，允许和拒绝都审计。`wake` 和 `logs.read` 还不能远程调用。
- `config.write` 的参数是配置文件本身的 JSON，不是 `config.read` 的视图。写入后 `access` 立即生效，其余字段留在文件里，重启后生效。不能改 `data_dir`。
- 本机调用方看到的错误码：`denied`（拒绝访问）、`unreachable`（离线/不可达）、`timeout`（超时）、`not_found`（名录里没有）。
- 不引入中继；仍然直连、TLS 指纹固定。查询不会为了读去唤醒对方。

## 8. 进程与打包

```
容器
├─ billgod   核心：节点、协议、执行、远程控制 API、Unix socket
└─ billui    可选：登录、页面、调用本机 billgod
```

- 入口脚本先启动 `billgod`，等 Unix socket 可用后再启动 `billui`。
- `billui` 连不上 `billgod` 时重试并输出明确日志；`billgod` 不关心 `billui`。
- 两个二进制打进同一镜像；发行包同时包含。
- `billui` 不持有权威状态；session 在内存，密码每次启动重置。
- `billgod` 不再监听页面端口，`ui` 配置从节点配置中移除。

## 9. 迁移步骤

**阶段一：billgo 远程只读**（已完成）

- 控制信封、动作目录、`access` 配置、审计日志；
- `billgo --peer` 查询 `node` / `config` / `peers` / `ticket list` / `ticket show`，工单分页；
- 拒绝、离线、超时、名录里没有，四种错误可区分。

**阶段二：billui 骨架**（已完成）

- `billui` 二进制：登录、密码每次启动重置、会话只在内存；
- 本机状态、配置摘要、名录、分页工单；
- 点开邻居时按需读取。拒绝和离线只显示错误，不留上次内容。

**阶段三：剥离 UI**（已完成）

- 删除 `internal/webui` 和节点 `ui` 配置；
- 镜像入口先起 `billgod`，再起 `billui`。`BILLUI=0` 可以不要页面。

**阶段四：远程写**（已完成）

- `tickets.create`、`tickets.redispatch`、`tickets.void`、`config.write`；
- 写默认拒绝；允许和拒绝都审计；同一 `body.id` 不重复执行；
- `config.write` 落文件，只有 `access` 立即生效；
- `billgo --peer` 可以发起、改派、作废和 `config write --file`；
- billui 可以发起、改派、作废。改配置仍用命令行。

**阶段五：打磨**（已完成）

- 本机审计页和 `billgo audit`，按时间倒序分页；
- 读默认开放时，节点启动打警告，billui 首页也提示。写仍然默认拒绝；
- 登录页说明密码只在这次进程里有效，忘记就重启；
- 拒绝、离线、超时不自动重试，只提供手动再试；
- 工单列表一次扫完事件桶，单张工单按键前缀读取。游标格式不变。

## 10. 影响面

- 删除：`internal/webui`、节点 `ui` 配置、页面相关测试；
- 新增：`internal/control` 远程协议、动作权限、审计、billui 工程；
- CLI：新增 `--peer`，删除 `node`（并入 `status --me`），`config` 支持读写；
- 文档：旧的《前端页面设计》《前端页面开发计划》已删除，由本文和后续的 billui 设计取代；
- 部署：同容器双进程，入口脚本与健康检查调整。

## 11. 已定

- 第一版不做 `jobs.read`、`outbox.read`。`logs.read` 只留在动作目录里，还不能调用。
- `access.rules` 用数组。匹配顺序见 5.2。
- 写默认拒绝，不受 `default: allow` 影响。
- 分页游标是 `updated_at|id`，不在服务端留快照。
- 审计按 8MB 轮转，保留 3 个旧文件。
- `config.write` 落文件后重启生效；只有 `access` 立即生效，否则撤不了权。已按此实现。
- billui 密码只打日志，并写入 `<data_dir>/billui.password`（0600）。不读环境变量。
- 被拒绝、离线、超时都不自动重试。页面说明原因，并给出「再试一次」。点下去才再问一次，不保留上次内容。拒绝不会因为重试变成允许。

## 12. 验收

1. `billgod` 启动后没有页面端口，`billgo` 能独立完成所有动作。
2. `billui` 在 `billgod` 之后启动，登录后能看到本节点。
3. 选择一个邻居，能按页加载它的工单；没有“加载全部”入口。
4. 邻居拒绝时显示“拒绝访问”；邻居离线时显示“离线”，不展示旧数据。
5. 修改 `access` 规则后，远程读写按规则生效。
6. 每个远程读写请求在目标节点留下审计记录，允许和拒绝都有。
7. 重启 `billui` 后密码变化、会话失效。
8. 发起者宕机后，工单在其他节点的 UI 中不可见；唤醒后重新可见。
