# billgo 功能说明

billgo 是一个**去中心化的 Agent 工单工具**：一个二进制，既是节点也是 CLI。每个节点本地持有完整名录；工单由发起者持有，接活方只做自己那一跳，并留一张签名回执。

面向内网、几十到几百个 Agent 的场景，目标是让 Agent 之间派活不依赖一个中心队列。

## 1. 解决什么问题

- Agent A 要把任务交给 Agent B，并拿回交付物；
- 不希望所有工单都存在一个中心服务里；
- 发起者要能掌握整张工单，接活方不需要知道上下游；
- 每条消息都要能证明“是谁说的、内容有没有被改”；
- 节点可能常驻，也可能平时睡着、按需唤醒。

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| 节点 / Agent | 容器里的一个进程，既能发起工单，也能接活；分常驻类和唤醒类 |
| peer_id | 身份，等于公钥指纹的前 16 位；不依赖任何中心签发 |
| 名录 | 每个节点本地的完整 Agent 列表，记录由主人签名 |
| 工单 | 表单 + 流转图；发起者持有全部内容 |
| 跳 | 流转图里的一步；一次只交给一个节点 |
| 回执 | 接活方签名的交付凭证：工单号、跳号、内容哈希、时间 |
| 交付物 | 按内容哈希存放的文件；重复内容只存一份 |
| 唤醒 | 叫醒一个休眠容器；支持 SSH 和本机 docker 两种方式 |
| 适配器 | 把 billgo 的作业契约翻译成具体 Agent 的调用方式 |

## 3. 功能清单

### 3.1 身份与安全

- 每个节点生成 ed25519 密钥，`peer_id = base32(sha256(公钥))[:16]`。
- 所有 Agent 之间的消息都是签名信封，签名覆盖除签名字段外的全部内容。
- 传输用自签 TLS 证书；连接时核对证书公钥指纹，不信任任何 CA。
- 接活方只接受 `allow_from` 里的 peer_id 派来的工单；空列表表示全部拒绝。
- `hop.*` 消息有 5 分钟重放窗口；重复消息通过幂等键去重。

### 3.2 发现与名录

- 每个节点持有完整名录，不依赖中心注册服务。
- 记录由主人签名，带自增版本号；版本大的胜出。
- 注销写墓碑，永久保留，防止离线节点把删除的记录“复活”。
- 新节点只配一个 bootstrap 邻居（`https://host:port#peer_id`），其余节点靠广播和反熵发现。
- 每 60 秒随机与一个节点做一次反熵，补齐缺失或过期的记录。
- 不同 `network` 是不同域，记录互相隔离。
- 存活不写进名录；派单前用 `/health` 现查。
- 唤醒类节点不心跳，睡着时仍留在名录里；注销需要显式执行。

### 3.3 工单流转

- 发起者创建工单：自由 JSON 表单 + 线性流转图。
- 发起者持有表单、流转图、每跳状态和交付物；接活方只保存自己那一跳的回执。
- 每跳流程：派单 → 接受 / 拒绝 → 交付 → 发起者核验 → 下一跳。
- 拒绝或超时后，发起者可以改派另一个节点，或作废整张工单。
- 每跳有超时：受理超时默认 30 分钟，交付超时默认 120 分钟。
- 工单状态由追加写的事件日志推导，不单独维护状态表。
- 发起者宕机，工单即丢失；这是去中心化的设计取舍，不做复制。

### 3.4 投递与可靠性

- 出站信封先落盘到 outbox，再投递；至少一次投递。
- 失败按 1s、2s、4s… 退避，上限 5 分钟。
- 接收方用 `(工单号, 跳号, 类型)` 去重，重复投递不会重复干活。
- 交付物按 sha256 内容寻址，两端各存一份。
- 每次重试前刷新时间戳并重签，避免长重试撞上重放窗口。

### 3.5 Agent 执行

- 节点通过 `agent_cmd` 启动执行进程；billgo 不关心它是什么 Agent。
- 每次作业提供：
  - `$BILLGO_JOB_DIR/job.json`：工单号、跳号、发起者、表单；
  - `$BILLGO_OUT_DIR`：交付物目录；
  - `BILLGO_TICKET`、`BILLGO_HOP`、`BILLGO_FROM` 等环境变量。
- 退出码 0：打包交付物、签回执、发交付消息。
- 退出码非 0 或超时：读取 `$BILLGO_JOB_DIR/result.json` 的 `reason`，作为拒绝原因发回。
- 每个节点同时只执行一个作业，其余在内存中排队。
- 作业状态落库，节点重启后会重新执行未完成的作业。
- 执行日志在 `data/jobs/<工单号>-<跳号>/agent.log`。

### 3.6 唤醒

- 常驻类节点一直运行；唤醒类节点平时是停止的容器。
- 唤醒方式：
  - `ssh`：连到宿主机，由 `authorized_keys` 里的强制命令执行 `docker start`；
  - `local`：直接执行 `docker start`（适合宿主机部署，或容器挂载 docker socket）。
- 派单前先查 `/health`，不通才唤醒；叫醒后轮询就绪再发信封。
- 唤醒类节点优雅退出不写墓碑，睡着后仍可被叫醒。

### 3.7 本机页面

- 独立进程 `billui`，默认监听 `127.0.0.1:7878`。`BILLUI_LISTEN` 可以是别的地址。`BILLUI=0` 时容器不启动它。
- 每次启动生成新密码，写入 `<data_dir>/billui.password`（0600），并打到日志。会话在内存里，重启即失效。
- 登录后可以看本节点的状态、配置摘要、名录和分页工单，也可以点开邻居看它当前的配置和工单。
- 身份、名录和工单列表按约定公开，配置里不能拒绝。列表不含表单。配置或工单内容被拒时，页面留下能看的部分，内容页显示「内容不可见」。离线显示「离线/不可达」，超时显示「超时」。都不自动重试，可以点「再试一次」。
- 读默认开放时，首页会提示邻居能读到工单和配置。审计页只看谁访问过本机。
- 页面上可以发起、改派、作废。改配置用 `billgo config write --file`。

### 3.8 CLI

```text
billgo [--data 数据目录] <命令>

version                 版本
node                    最小身份信息（peer_id / name / kind / endpoint / network / version）
status                  状态、待处理与配置摘要
config                  当前生效配置
config write --file f   写入配置（access 立即生效，其余重启后生效）
audit                   本机审计，可加 --limit 和 --cursor
peers                   本地名录
ticket create           发起工单
ticket list             工单列表
ticket show <id>        工单详情与事件流
ticket redispatch       改派某跳
ticket void             作废工单
outbox                  待发队列与重试次数
wake <节点>             手动唤醒
withdraw                注销自己（写墓碑）

--peer <节点> node|config|peers
--peer <节点> config write --file <cfg.json>
--peer <节点> ticket list [--limit N] [--cursor C]
--peer <节点> ticket show <id>
--peer <节点> ticket create|redispatch|void ...
```

`--peer` 让本机节点去问邻居。读默认允许，写要对方在 `access` 里显式放行。拒绝、离线、超时、名录里没有，是四种不同的错误。数据目录默认 `data`，也可用 `BILLGO_DATA` 指定。

### 3.9 配置

- 一个 JSON 配置文件，`billgod -config billgo.json`。
- 主要字段：节点名、类型、域、监听地址、对外地址、数据目录、bootstrap、白名单、唤醒方式、`agent_cmd`、各类超时。
- 环境变量可以覆盖部分字段，优先级：**环境变量 > 配置文件 > 默认值**。
- 启动时统一校验：非 loopback 页面监听、非法 bootstrap、非法的 Agent 类型都会被拒绝。

### 3.10 部署

- 单个静态二进制，无外部依赖；入口是守护进程 `billgod`、命令行 `billgo`、可选页面 `billui`。
- 提供 Linux / macOS / Windows × amd64 / arm64 的发行包和安装脚本。
- 有 Docker 镜像；数据目录必须挂卷，否则身份会变。
- 多节点只需要一个 bootstrap 邻居；容器之间用服务名互相访问。

## 4. 典型流程

**两个节点完成一张工单**

1. banana 先启动，`bootstrap` 留空，读出它的 peer_id；
2. apple 启动，`bootstrap` 指向 banana；
3. apple 创建工单，流转图是 `banana → peach`；
4. banana 接受、执行、交付；apple 核验后派给 peach；
5. peach 交付；apple 收齐两份回执，工单关闭。

**拒绝与改派**

1. peach 拒绝，或超时未受理；
2. 发起者在 `status` 里看到待处理项和可复制的改派命令；
3. 执行 `ticket redispatch` 换一个节点，或 `ticket void` 作废。

**唤醒类节点接单**

1. 工单指向一个停止的容器；
2. 发起者先 `/health`，失败后按记录里的唤醒方式启动容器；
3. 容器起来、就绪后收到派单，执行并交付。

## 5. 边界

当前不做：

- 并行、分支、汇合（DAG）；只支持线性流转。
- 工单携带二进制附件；表单只能是 JSON。
- 交付物原始文件名和 MIME 类型；下载名是通用占位名。
- 发起者故障恢复或工单复制。
- 页面多用户、角色；`billui` 只有一把启动密码。
- 交付物自动回收、配额、GC。
- NAT 穿透、跨网中继、libp2p、DHT。
- 每节点并发执行多个作业（固定为 1）。
- 接活方的策略引擎（只有接受 / 拒绝两个出口）。

适用的场景：

- 内网、机器地址稳定；
- 几十到几百个 Agent；
- 任务可以顺序流转；
- 交付物以文件为主；
- 需要回执和审计线索。
