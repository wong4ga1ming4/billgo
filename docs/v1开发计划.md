# Billgo v1 开发计划

配套文档：《全流程设计.md》。本文只规划 v1，范围是**内网、线性工单流转、可演示的三节点闭环**。

> **状态（2026-11-15）：M0–M8 已完成。**
> `go test -race ./...` 全绿；`scripts/e2e.sh`（真实二进制）、`deploy/up.sh`（三容器）与 `scripts/e2e-wake.sh`（停止的容器被 local 唤醒）均跑通。
> 实现与本文的差异：WebSocket 未做（v1 全部走 HTTP）；唤醒在 ssh 之外增加了 `mode: "local"`；唤醒类节点优雅退出不写墓碑，注销需显式 `billgo withdraw`；控制面 socket 路径受 Unix socket 长度限制（约 104 字节），数据目录不宜过深。

## 1. v1 的验收标准

一条命令就能看到：

> 在三个容器（banana / apple / peach）里跑起来，apple 创建一张工单，peach 是唤醒类先被叫醒，接活、干活、交付，apple 核验通过并留下回执；中途杀掉 peach 的容器，重试后工单仍然能走完。

具体验收项：

- [ ] 新节点只配一个 bootstrap 地址，30 秒内能在所有节点名录里看到。
- [ ] 注销后，墓碑在所有节点生效，重启的旧节点不会把它复活。
- [ ] 常驻类和唤醒类各跑通一次完整工单。
- [ ] 节点在 `hop.deliver` 前重启，重启后能把已受理的作业做完并交付。
- [ ] 重复投递不重复干活，返回上一次的响应。
- [ ] 工单被拒绝后，发起者能改派另一个节点。
- [ ] `billgo ticket show <id>` 能打印完整事件流。

## 2. 范围

**做：**

| 模块 | 内容 |
|---|---|
| 身份 | ed25519 密钥、`peer_id` 指纹、密钥落盘 |
| 存储 | bbolt（peers / tickets / receipts / outbox / dedupe）+ blobs 目录 |
| 信封 | 规范化 JSON、签名验签、幂等键、重放窗口 |
| 传输 | HTTP POST + `GET /health`，TLS 自签证书绑指纹 |
| 名录 | 自签名记录、变更广播、60 秒反熵、墓碑、bootstrap |
| 工单 | 线性 `flow`、事件日志、每跳状态机、拒绝改派、超时 |
| 接活 | 策略自动接受、job 目录、驱动 Agent 进程、内容寻址交付、签名回执 |
| 唤醒 | SSH 强制命令 + 唤醒脚本 + `/health` 轮询 |
| 投递 | outbox 退避重试 |
| 前端 | 一个 CLI（`ticket` / `peers` / `wake` / `outbox`），本地 Unix socket |
| 打包 | 单二进制、Dockerfile、三节点 compose 示例 |

**不做（v1）：**

- DAG、并行、汇合（数据模型预留 `depends_on`，校验强制成链）。
- WebSocket 长连接。v1 全部走 HTTP，够用且少一大块重连逻辑。
- MCP 接口、Web UI、metrics 服务。
- 工单复制、发起者故障恢复。
- 交付物自动回收、记录淘汰、跨域联邦。
- 策略引擎：接受只有"白名单 + 描述匹配"这一种。
- 唤醒凭证的自动分发。

## 3. 流转模型

`flow` 是数组，每项一个跳：

```json
{
  "step": 1,
  "to": "<peer_id>",
  "depends_on": [],
  "desc": "写一份接口文档"
}
```

v1 校验规则（写死在创建工单时）：

- 第一跳 `depends_on` 为空，之后每跳恰好依赖上一跳；
- 不能重复出现同一节点；
- 至少一跳。

这样数据结构天然兼容 DAG，只是 v1 的校验器不接受。将来去掉校验即可，信封和存储不用改。

## 4. 仓库结构

新开一个 Go module，不复用 pigw 的依赖树，只**复制**少量骨架代码：

```
billgo/
  go.mod
  cmd/billgod/main.go     节点守护进程
  cmd/billgo/main.go      CLI
  internal/config/           配置文件
  internal/identity/         ed25519、peer_id
  internal/store/            bbolt 桶、事件写入
  internal/envelope/         规范化、签名、验签、幂等
  internal/transport/        HTTP 服务端/客户端、TLS 指纹固定
  internal/peers/            记录、广播、反熵、墓碑
  internal/ticket/           flow 校验、事件、状态机
  internal/outbox/           重试投递
  internal/job/              job 目录、驱动子进程、收集输出
  internal/wake/             SSH 唤醒
  internal/control/          Unix socket 本地接口
  scripts/wake.sh            被唤醒方的脚本
  deploy/docker-compose.yml  三节点示例
```

依赖只有：`go.etcd.io/bbolt`、标准库。TLS、HTTP、SSH 全部走标准库或直接调 `ssh` 命令。

## 5. 里程碑

按"先竖着打通一条线，再横着补厚度"排序。估算是单人、熟悉 Go 的前提下的人日，上下浮动 30%。

### M0 · 骨架（0.5 天）

- 建 module、目录、配置加载、日志。
- 启动时生成或加载 ed25519 密钥，算出 `peer_id`。
- bbolt 建桶，写入 schema 版本号（将来迁移用）。

**完成标志**：`billgod` 能启动、打印自己的 `peer_id`、优雅退出。

### M1 · 信封与存储（2 天）

- 规范化 JSON（字段排序、整数、毫秒时间戳）。
- 信封结构、签名、验签、`from` 指纹核对、`to` 核对。
- 重放窗口（仅 `hop.*`）、幂等键查 `dedupe`。
- 单元测试：改一个字节验签失败、重放被拒、重复请求返回缓存响应。

**完成标志**：进程内两个节点互发一封信封，验签通过；篡改任一字段失败。

### M2 · 传输与健康检查（1.5 天）

- HTTP 服务端：`POST /envelope`、`GET /health`。
- 客户端：带超时、连不上的错误分类。
- TLS：自签证书，`VerifyPeerCertificate` 校验指纹。
- 单测用 `httptest`。

**完成标志**：两个进程互相认证、请求成功；指纹不符时连接被拒。

### M3 · 名录（3 天）

- 记录结构、自签名、版本号、墓碑。
- 本地 `peers` 表写入与冲突规则。
- 启动时向 bootstrap 发 `peers.digest` → `peers.sync` 拉全量。
- 变更广播；60 秒反熵循环；逐条应用。
- 从信封学习地址。

**完成标志**：三个进程内节点，任意一个改记录，其余两个 60 秒内看到；注销后所有节点都是墓碑；重启旧节点不会复活记录。

### M4 · 工单发起侧（3 天）

- `ticket create`：flow 校验、`ticket.created` 事件、返回 id。
- 每跳状态机：`hop.sent` →（accept/reject/timeout）→ `hop.delivered` → `hop.verified`。
- 超时扫描（受理 30 分钟、交付 2 小时，可配置）。
- 拒绝后改派：`ticket.amended`。
- `ticket list` / `ticket show`，事件流打印。

**完成标志**：发起侧对着一个假节点（返回固定 accept/deliver）走完一张两跳工单；拒绝后能改派；超时能落到 `expired`。

### M5 · 接活侧（3 天）

- 收 `hop.issue`：验签、幂等、策略判断（白名单 + 描述匹配）。
- 自动接受 → 写 job 目录（`job.json`）→ 启动 Agent 子进程（复制 pigw 的 `driver/oneshot` 骨架）。
- 退出码决定路径：0 = 打包 `out/`、算哈希、签回执、发 `hop.deliver`；非 0 = 读 `result.json` 发 `hop.reject`。
- blobs 落盘（内容寻址）。
- 作业状态写库，进程重启后能继续。

**完成标志**：一个 echo 脚本作为"Agent"，端到端完成一次交付；daemon 重启后未完成的作业继续跑完。

### M6 · 唤醒与投递（2 天）

- `scripts/wake.sh`：硬编码容器名、输出 JSON。
- 发起侧：派单前 `GET /health`，不通就 SSH 唤醒，再轮询（30 秒）。
- outbox：写入 → 退避重试（1s/2s/4s…上限 5 分钟）→ 成功标记。
- 唤醒失败、SSH 失败、health 超时的错误分类。

**完成标志**：真实容器场景下，peach 处于停止状态，工单仍能走完；拔掉网络 30 秒，恢复后继续。

### M7 · 端到端与打包（2 天）

- `deploy/docker-compose.yml`：banana + apple + peach。
- Dockerfile（静态编译、多阶段）。
- 端到端测试脚本，覆盖验收标准的每一条。
- README：三分钟跑通。

**完成标志**：新机器上 `docker compose up` 后，一条命令看到完整闭环。

### M8 · 打磨（1.5 天）

- 日志分级、关键路径的结构化日志。
- 错误信息可读（验签失败要说清是哪一端）。
- CLI `--json` 输出。
- 处理首批真实使用中暴露的边角问题。

**合计约 16 人日**（含测试），日历时间 3 周左右。

## 6. 排序理由

- **M1 → M2 先竖通**：信封和传输是所有模块的地基，且最容易在早期暴露设计问题。
- **M3 独立于工单**：名录可以单独验证，不依赖工单逻辑。
- **M4、M5 可以并行**：两个方向靠协议对接，一人写发起、一人写接活，中途用假节点对接。
- **M6 放最后**：唤醒是运维集成，不影响主流程的代码结构，晚做不会返工。
- **M7 尽早开始**：compose 环境从 M2 起就可以搭，越早真实环境越好。

## 7. 测试策略

| 层 | 手段 | 覆盖 |
|---|---|---|
| 单元 | Go testing | 规范化、签名、版本冲突、flow 校验、状态机迁移 |
| 多节点 | 进程内起 3 个节点 + `httptest` + 临时目录 | 广播、反熵、墓碑、幂等、超时 |
| 端到端 | compose + 真实容器 + 简单脚本 Agent | 验收清单全部 |
| 韧性 | e2e 中注入：杀容器、断网、重启 daemon | 投递重试、作业恢复、幂等 |

不引入测试框架，标准库 `testing` 足够。

## 8. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| Agent 进程与 daemon 的作业协议反复变 | M5 返工 | job 目录 + 退出码是最小契约，先冻结，复杂交互留到 v2 |
| 规范化 JSON 两端不一致 | 验签随机失败 | v1 只有 Go，一处实现，加跨版本回归样例 |
| SSH 在容器内的可用性（客户端、known_hosts、密钥挂载） | M6 延期 | M2 起就在 compose 里放好 ssh 客户端和测试密钥 |
| 发起者宕机丢工单 | 使用方预期不符 | README 明确写为设计约束 |
| 唤醒类地址不稳定（容器 IP 变化） | 派单失败 | 记录里固定 `host:映射端口`，不记录容器 IP |
| 范围膨胀（DAG、MCP、UI） | 工期失控 | 本文第 2 节的"不做"清单即为范围防线 |

## 9. 第一个可演示版本

如果只想要一个能看的 demo，按 M0 → M1 → M2 → M4 → M5 的"假名录 + 硬编码节点"路径，**约 8 天**可以跑通"apple 发起 → peach 交付 → apple 核验"。名录和唤醒可以先用配置文件里的静态记录代替。

## 10. 后续（v2 候选）

按优先级：

1. WebSocket 推送（减少轮询延迟）。
2. DAG 流转（放开 `depends_on` 校验、增加汇合语义）。
3. MCP 接口。
4. 交付物回收与记录淘汰。
5. 跨网（WireGuard 组网优先于打洞）。
