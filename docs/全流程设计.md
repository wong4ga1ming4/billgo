# 去中心化 Agent 通信 · 全流程设计

本文是讨论后的定稿，描述工具从上电到一张工单走完的完整流程。原始想法见《设计文档.md》，两处冲突以本文为准。

## 1. 设计原则

1. **权威跟着数据走。** 工单的全部内容、流转图、每一跳的交付物，都只在发起者本地。接活方只负责这一个环节，只留一张签名回执。
2. **身份自证。** Agent 的身份是公钥指纹，不是任何中心签发的名字或证书。
3. **名录是数据，不是服务。** 每个 Agent 本地持有完整名录，每条记录由它的主人自签名。转发名录的节点不是权威：它只能让你知道得慢一点，不能替你伪造任何人。
4. **先落盘，再发送。** 任何要发出去的东西先写本地库，再进 outbox 投递。进程随时可以死。
5. **内网假设。** v1 的部署环境是同内网、地址可达。不做 NAT 穿透、不做 DHT、不引入 libp2p。地址写在数据里，不写在代码里，将来换环境只改地址来源。

## 2. 角色

| 角色 | 是什么 | 常驻 | 被谁访问 |
|---|---|---|---|
| Agent | 容器里的一个进程，既能发起工单，也能接活，同时持有完整名录 | 常驻类 / 唤醒类 | 接活方必须可被访问；只发起不接活的可只出站 |
| Host 通道 | 机器上的 sshd，用于唤醒容器 | 已有 | 发起方的 Agent |

**没有注册中心。** 名录不是某个服务里的数据，而是每个 Agent 本地的一份副本，靠广播和反熵保持一致。新节点接入时只需要在配置里写一个已知节点的地址（bootstrap），把名录拉下来，之后它自己就是别人的 bootstrap 之一。

**唤醒通道归 host，不归 Agent。** 睡着的 Agent 没有连接，叫醒它只能找它所在的机器。这条通道是整套系统里权限最大的东西，见第 9 节。

## 3. 身份

- 每个 Agent 启动时生成一对 ed25519 密钥，私钥落盘，权限 0600。
- **身份标识 peer_id = base32(sha256(公钥)) 的前 16 个字符。** 完整指纹另存。
- 同一把密钥复用三处：签名信封、TLS 自签证书、SSH 唤醒凭证。不维护第二套身份。
- 名字只是别名，**不唯一，也没有先到先得**——名录是复制的，不存在能裁决先后的全局顺序。展示时写成 `peach#a1b2`（名字 + 指纹前四位）。名字不承担任何安全属性；收到任何东西都先按信封里的公钥算指纹核对。

## 4. 本地存储

每个 Agent 一个数据目录，内含一个 bbolt 文件加一个 blobs 目录。所有 Agent 的库结构完全一样，角色差异只由配置决定。

| 位置 | 内容 | 谁写 |
|---|---|---|
| `peers` | 完整名录：peer 记录 + 墓碑，每条带 owner 版本号 | 自己写自己的；别人的靠广播和反熵同步进来 |
| `tickets` | 工单事件日志（追加写，不修改） | 发起者；接活方只写自己那几跳的回执索引 |
| `jobs` | 接活侧作业状态（running/delivered/rejected），用于重启后继续 | 接活方 |
| `receipts` | 签名回执：工单号、跳号、内容哈希、双方签名、时间 | 双方各留一张 |
| `outbox` | 待发出的信封：目标、字节、重试次数、下次时间 | 发送方 |
| `dedupe` | 已处理信封的幂等键 → 上次响应 | 接收方 |
| `blobs/<sha256>` | 交付物本体，按内容寻址 | 双方各自保存 |

工单状态不单独存一张表，由 `tickets` 事件日志推导。状态机见第 8 节。

交付物大文件不进 bbolt，只存哈希和元数据。

## 5. 协议：签名信封

所有 Agent 之间的消息都是同一个信封，传输层只是载体。

```
{
  "v": 1,
  "type": "hop.issue",
  "from": "<sender 公钥 base64>",
  "to":   "<约定中的接收者 peer_id>",
  "ticket": "<uuidv7>",
  "hop": 2,
  "ts": 1731600000123,
  "body": { ... },
  "sig": "<ed25519 签名 base64>"
}
```

- **签名对象是规范化后的字节**：字段按字典序、无多余空白、数字只用整数、时间用 Unix 毫秒。签名覆盖除 `sig` 外的全部字段。两端必须用同一套规范化实现，序列化不一致会导致收不到原因的验签失败。
- **重放保护**：`hop.*` 和 `ctl.*` 的 `ts` 与本机时间相差超过 5 分钟直接丢弃；同一个幂等键重复收到，查 `dedupe` 直接返回上次的响应，不重复执行。`peers.*` 不看时间。
- **接收方核对三件事**：签名有效、`from` 的指纹与信封里公钥一致、`to` 是自己。任一不对就丢弃并记录。

消息类型只有这些：

| type | 方向 | 作用 |
|---|---|---|
| `peers.record` | 记录主人 → 所有已知节点 | 广播自己的记录；`deleted: true` 的是墓碑 |
| `peers.digest` | 任意 → 任意 | 反熵：发一份 `peer_id → version` 摘要 |
| `peers.sync` | 任意 → 任意 | 反熵补齐：返回对方缺的或版本旧的记录 |
| `hop.issue` | 发起者 → 节点 | 派这一跳的表单 |
| `hop.accept` | 节点 → 发起者 | 受理 |
| `hop.reject` | 节点 → 发起者 | 拒绝，带原因 |
| `hop.deliver` | 节点 → 发起者 | 交付，带内容哈希和回执 |
| `ctl.request` | 任意 → 目标节点 | 远程控制请求，动作在 body 里 |
| `ctl.response` | 目标节点 → 发起者 | 控制响应，数据或错误码在 body 里 |

健康检查不走信封，就是 `GET /health`。

两条补充规则：

- **幂等键按类型定。** 工单消息用 `(ticket, hop, type)`；名录消息用 `(peer_id, version)`，版本不大于本地已知版本的一律丢弃；控制请求用 body 里的 `id`。
- **重放窗口管 `hop.*` 和 `ctl.*`。** `peers.*` 可能是被转发的，几分钟甚至几小时前的记录依然有效，靠签名和版本号判断，不看时间。

`peers.record` 由记录主人签名，转发者原样转发字节、不二次签名。收到后先按公钥算指纹核对 `peer_id`，再看版本。

`hop.confirm`（发起者回告节点"已验收"）不做。回执本身就是凭证，节点不需要再被通知一次。

## 6. 传输与安全

- **HTTP POST** 承载所有信封。v1 不开长连接：所有消息都由发送方主动发起，不存在服务端推送的场景，重连和心跳的复杂度不值得。
- **TLS 用自签证书**：每个 Agent 用自己的 ed25519 密钥签一张证书；连对方时校验 `cert.PublicKey` 的指纹等于自己记录里的指纹，不信任任何 CA。
- 由此得到：传输加密、身份绑定、前向保密。签名解决"谁说的"，TLS 解决"别人看不见"，两件事都需要。
- 内网也建议开着。成本是一个 `VerifyPeerCertificate` 回调，收益是内网里也没有明文工单。

## 7. 名录与发现

名录是每个 Agent 本地的一份完整副本，不是某个服务里的数据。

### 7.1 一条记录

| 字段 | 说明 |
|---|---|
| `peer_id` | 公钥指纹，唯一键 |
| `pubkey` | 完整公钥 |
| `name` | 别名，不唯一，只作展示 |
| `desc` | 自由描述，**发起者就是按它选节点的** |
| `kind` | `resident` / `wakeable` |
| `endpoint` | `https://host:port`，唤醒类醒来后才有效 |
| `wake` | `{mode: "ssh", target: "user@host", container: "peach", host_fp: "..."}`，唤醒类必填；`host_fp` 用来固定 SSH host key |
| `network` | 域标识，默认 `default`，不同域的记录互相丢弃 |
| `version` | owner 自增的整数，任何字段变化都加一 |
| `deleted` | 墓碑标记，注销时置为 true 并伴随 `version+1` |
| `sig` | owner 用自己的私钥签的签名 |

没有"上次心跳"字段。存活不靠名录证明，派单前 `GET /health` 现查。

### 7.2 记录怎么传播

1. **变更即广播。** 自己的记录一改（启动、改描述、改唤醒方式），原样推给所有已知节点，尽力而为，失败不管。
2. **反熵兜底。** 每 60 秒随机挑一个已知节点，互发 `peers.digest`（全部 `peer_id → version`），用 `peers.sync` 补齐缺的、旧的。推送失败的、离线期间错过的，都在这一步收敛。
3. **从信封学习。** 收到任何信封，把发送方实际使用的地址记成一条本地提示（覆盖记录里 owner 声明的 `endpoint`），公钥仍以记录为准。
4. **bootstrap。** 配置里写一到几个已知节点地址。新节点启动时向它们发一次空的 `peers.digest`，拿回全量，之后它自己就是别人的 bootstrap 之一。

所有来源写入同一张 `peers` 表，冲突规则只有一条：**版本号大的赢；版本相同时取内容哈希字典序较大的那条并记一条警告**。正常情况下版本相同内容不同不会发生，出现就说明有人在冒充篡改自己的记录。

### 7.3 注销与墓碑

注销就是发一条 `deleted: true`、`version+1` 的记录。

- **常驻类**：优雅退出（SIGTERM）时自动注销。
- **唤醒类**：**不自动注销**。睡着是它的正常状态，自动注销等于让别人再也找不到、也没法叫醒它。要下线就显式执行 `billgo withdraw`。

墓碑**永久保留**，不设过期。否则一个离线很久的节点回来，会把删掉的记录重新灌回全网（删除复活）。几十条墓碑的存储成本可以忽略。

### 7.4 存活

名录只回答"有谁、在哪、怎么叫"，不回答"现在活着吗"。

- 常驻类：派单前直接 `GET /health`，不到 200 就按对方不在处理。
- 唤醒类：先按 `wake` 叫醒，再 `GET /health`。
- 连不上的节点不会被自动删除——它可能只是暂时睡着的。要删就显式注销。

### 7.5 只发起不接活的节点

它没有入站端口，收不到广播。做法是只拉不推：每 60 秒主动向 bootstrap 或任一已知节点做一次反熵。这不影响它发工单，因为发工单只需要知道对方地址。

### 7.6 规模

这套复制在几十到几百个节点范围内够用：反熵流量随节点数线性增长，而不是平方。上千节点才需要分层或抽样，上万才轮到 DHT。v1 不做。

## 8. 工单全流程

用原始文档里的例子：banana 是最先在场、被 apple 配成 bootstrap 的节点，apple 发起，peach 接活。

### 8.1 创建

apple 生成 `uuidv7` 工单号，写 `ticket.created` 事件：

```
{ ticket, form, flow: [{step:1, to:<peach 指纹>, desc:"..."}, ...], ts }
```

`flow` 是创建时定下的流转图。选点依据是 peer 记录里的描述，人工指定或由 Agent 自动挑选，协议层不管。

### 8.2 走一跳

apple 本地名录里已经有 peach 的记录，不需要再去问任何人。如果还没有（比如 peach 刚接入），先向 bootstrap 做一次反熵拉取，再走下面的流程。

```
apple                                          peach (host: x)
  |
  |  (唤醒类：ssh host 'wake peach' → docker start)
  |
  |  GET /health  轮询直到 200 或 30s 超时
  |------------------------------------------------->|
  |  200
  |<-------------------------------------------------|
  |
  |  hop.issue (签名信封)
  |------------------------------------------------->|
  |  hop.accept / hop.reject
  |<-------------------------------------------------|
  |  ...
  |  hop.deliver {blob_hash, receipt}
  |<-------------------------------------------------|
```

apple 的每次动作都先写事件再发送：

1. `hop.issue` 发出前写 `hop.sent`，信封进 outbox。
2. peach 验签、去重、决定接受或拒绝。**接受与拒绝是它唯一的策略出口**，白名单、能力判断都放在这一步。
3. 接受后只做这一跳，把交付物按内容寻址落盘，签一张回执，`hop.deliver` 交回。
4. apple 核对签名、核对内容哈希和回执一致，写 `hop.delivered`，再派下一跳。

### 8.3 状态机

每一跳：

```
pending ──accept──> working ──deliver──> delivered ──verify──> done
   │                    │
   ├──reject──> rejected│
   └──timeout─> expired ┘
```

工单整体：`running → closed`（全部跳完成）或 `voided`（发起者作废）。

- **拒绝**回到 apple，由 apple 决定：从名录改派另一个节点，或者作废整张工单。发起者持有这张工单的全部权限。
- **超时**：`hop.issue` 之后 30 分钟无 `accept`/`reject`，apple 记 `hop.expired`，按拒绝处理。
- **接受后失联**：`accept` 之后 2 小时无 `deliver`，apple 记 `hop.expired`，同样按拒绝处理。与"明确拒绝"在事件日志里是两种事件，不合并。

### 8.4 拒绝后改派

apple 在 `flow` 里把这一跳的目标换掉，写一条 `ticket.amended` 事件，然后重新走 8.2。改派不追溯、不通知已完成的节点。

### 8.5 回执

peach 交付时留一张，apple 收到时也留一张，内容相同：

```
{ ticket, hop, blob_hash, from, to, ts, sig }
```

回执证明"这一跳发生过、交付物是这一份"。apple 手里的回执再加自己的签名，就能向第三方证明；peach 手里的回执证明自己交付过。两边各留一张，谁都不依赖对方。

## 9. 唤醒

唤醒有两种方式，都不进信封协议，写在 peer 记录的 `wake` 字段里。

### 9.1 ssh（默认）

- 凭证由**使用方**手工配置，工具不负责分发、不提供接口去加。几十台机器的规模，手工清单反而更可靠：谁能在什么时候叫醒谁，本身就是应该被有意识变更、可审计的事。
- 被唤醒方的 `authorized_keys`，每个（发起者，Agent）一行：

```
restrict,command="/opt/billgo/bin/wake peach" ssh-ed25519 AAAA... apple
```

- `wake` 脚本硬编码容器名，只做三件事：核对调用方（sshd 已完成）、`docker start peach`、输出一行 JSON。`restrict` 关掉 PTY 和端口转发，参数不让外部拼接。
- 发起方连 SSH 时用记录里的 `host_fp` 固定主机指纹，防内网冒充。
- 权限边界在 sshd：billgod 本身不需要任何 docker 权限，也就能叫醒被授权的那几个容器。

### 9.2 local（本机）

- 记录写成 `{"mode": "local", "container": "peach"}`，billgod 直接执行 `docker start peach`，容器名做字符集校验。
- 两种部署适用：billgod 跑在宿主机上；或者跑在容器里但挂载了 `/var/run/docker.sock`。
- **后者的代价要说清楚**：挂载 docker socket 等价于把宿主机 root 交给容器。工具自己只执行一条固定的 `docker start`，但权限边界由部署决定，不在工具里。不接受这个代价就用 ssh。
- 不需要 docker CLI 的构建可以加 `--build-arg WITH_DOCKER_CLI=0`。

### 9.3 两种方式共有的规则

- **唤醒成功不代表能接单。** 必须再轮询 `GET /health` 到 200（30 秒超时），才发 `hop.issue`。
- 唤醒失败不特殊处理：信封已经在 outbox 里，退避重试时再唤醒一次即可。

健康接口的口径 v1 定为：**进程已就绪、TLS 已监听、可以验签接单**。不表示空闲。

## 10. 投递保证

目标：**至少一次投递 + 幂等执行**，发起者不需要知道接收方此刻在不在。

1. 任何出站信封先写 `outbox`，状态 `pending`。
2. 投递成功（收到对应响应）即标记完成；失败按 1s、2s、4s… 退避，上限 5 分钟，一直重试直到成功或工单被作废。
3. 接收方用 `(ticket, hop, type)` 去重，重复请求直接返回上次响应。所以重试不会重复干活。
4. 交付物按内容寻址，同一个文件重复交付自然只存一份，回执里的哈希天然稳定。

每次投递都是独立的 HTTP 请求，用完即断。重试由 outbox 负责，不依赖连接是否保持。

## 11. 失败与边界

| 情况 | 结果 |
|---|---|
| 节点拒绝 | 回到发起者，改派或作废 |
| 节点接受后失联 | 超时按拒绝处理，改派 |
| 节点容器被删 | 唤醒失败，重试到超时，按拒绝处理 |
| 发起者宕机 | **工单直接没了。** 这是去中心化的必然代价，设计上接受，不做复制、不做恢复 |
| 任一节点宕机 | 名录不受影响，只是少了一个传播源；反熵会从别的节点补齐 |
| 名录暂时不一致 | 新节点的记录还没传到所有人。等下一次反熵或主动拉取；派单前 `GET /health` 现查，不影响工单 |
| 内网地址变了 | owner 更新记录并广播，各节点按版本号采纳；发起方按新地址重试 |
| 节点回来带着旧记录 | 版本号比本地小，直接丢弃；已注销的会被墓碑挡住，不会复活 |
| 重复投递 | 幂等键拦住，返回上次响应 |

发起者宕机后，节点上可能留下已交付但无人认领的交付物和回执。v1 不做自动回收，由使用方清理。

## 12. v1 明确不做

- NAT 穿透、ICE/STUN、DHT、libp2p、跨网中继。
- WebSocket 长连接（全部走 HTTP POST）。
- Merkle / bloom 反熵优化、记录淘汰、跨域联邦（墓碑永久保留）。
- 工单复制与发起者故障恢复。
- 表单的 schema 校验（自由 JSON）。
- 接活方的策略引擎（只有接受 / 拒绝两个出口）。
- 静态加密（TLS 已覆盖传输；磁盘加密交给宿主机）。
- 唤醒凭证的自动分发与轮换。
- 交付物的自动回收。
- 对节点的"已验收"回告。

## 13. 待定

1. **重名的展示**：名字已经不唯一，展示用 `名字#指纹前四位`。是否允许本地给节点起备注名（只对自己生效）？倾向于 v1 不做。
2. **节点并发**：一个节点同时收到多张工单时排队还是并行？v1 倾向于让节点自己决定，协议不限制。
3. **选点自动化程度**：v1 人工指定流转图，还是由发起方 Agent 读描述自动选？协议无关，但要定第一个版本的行为。
4. **回执的第三方验证**：回执和老工单一起离开发起者才有审计意义，是否需要导出格式？v1 不做，预留字段。

## 14. 与现有 Gateway 的关系

现有 [gateway-go](../gateway-go/) 是可复用的底座，但要丢掉的比留下的多：

- **留**：`internal/runtime`（容器拉起）、`internal/nodelink` 的连接与重连骨架、`internal/driver`（Agent 进程驱动）。
- **丢**：`internal/api`、`internal/dispatch`、`internal/queue` 以及 redis 依赖——这些正是中心的来源。
- **新写**：信封协议、bbolt 存储、自签名 peer 记录与反熵、工单事件日志、outbox、唤醒脚本。
